# Research: Flat Terminal Compatibility

- Query: What is the minimum compatible projection/model change for one worktree terminal surface with individual flat titlebar tabs, including every terminal in legacy panels/leaves, without replacing PTYs or changing live Agent route identities?
- Scope: internal, source-only planning for `.trellis/tasks/09-06-native-terminal-navigation` and parent `.trellis/tasks/09-06-native-ui-remote-feedback`; neither planning task was activated.
- Date: 2026-09-06
- Output owner: `.trellis/tasks/09-05-sidebar-agent-status/research/09-06-flat-terminal-compatibility.md` only.
- Constraints: No product/spec/PRD/metadata edits, git operations, local runtime, builds, Cargo metadata, tests, fixtures, probes, lint, formatting, code generation, automated verification, CI dispatch, or subagent dispatch. Automated evidence must come from GitHub Actions after implementation approval. Right ContextPanel ownership is accepted from the dispatch, not re-researched.

## Findings

### Recommendation

**Keep the existing terminal owners and saved trees; flatten their presentation, not their routing identities.** Add a worktree-layout selected-terminal pointer, enumerate every owning panel's complete pane list into one titlebar row, and render just the selected pane's existing `TerminalPane` entity. Remove user-facing split/group actions and rendering paths. This requires no new terminal identity type, PTY backend, Agent route schema, or replacement terminal collection.

For the lossless-tree approach, the minimum persistent model addition is one optional `PaneKey` selection field on `SavedProjectLayout`, with a corresponding runtime field on its layout-bearing state. Existing `activeTabId` continues to mean the owning legacy panel, not the visible tab's new identity. An independent flat ordering list is needed only if arbitrary cross-panel tab reorder is retained; it is not necessary just to expose and select every terminal.

This is a recommendation from source inspection, not an implemented or validated design. A smaller-schema alternative that collapses leaves *within each original panel* is discussed below; it can preserve routes, but rewrites legacy geometry and is not the recommended lossless projection.

### Identity Is Not the Visible Tab Position

- `ProjectPanel.tab_id` is the stable owner of a complete legacy tree (`tree.rs:209`). Each `PaneState` independently contains `pane_key`, logical `terminal_session_id`, optional incarnation, compatibility string `id`, and process-local `pty_id` (`tree.rs:98`). `id` is the `PaneKey` string projection, not a leaf/group ID.
- Terminology matters: the stable pane identity in this source is `PaneKey`, not a new `PaneId` type. The numeric `pty_id` is also called `pane_id` by legacy AI code (`tree.rs:110`). Keep both unchanged for an already-attached terminal. `AiSessionRef.session_id` is a provider conversation identity (`tree.rs:85`), separate from `TerminalSessionId`; neither should become the titlebar widget key.
- `MINITERM_TAB_ID`, `MINITERM_PANE_KEY`, and `MINITERM_TERMINAL_SESSION_ID` are injected at PTY start (`store/panes.rs:881`). SSH launch receives the same complete route (`store/panes.rs:911`, `store/panes.rs:923`). Moving an attached pane to a different owning `TabId` cannot update its existing child-process environment.
- Resolution requires the pane still to be under its original panel `TabId`: `terminal_binding_matches` checks that owner before pane/session/incarnation (`store/identity.rs:454`); Agent resolution does the same and also requires the exact terminal route and entity (`store/context.rs:325`, `store/context.rs:349`). Merely retaining `PaneKey` and PTY while assigning a new panel is insufficient.
- **Do not create one new `SavedTab` per old pane, merge all panels under one `TabId`, or reuse one old `TabId` in several new panel records.** The first two break owner routing; duplicate saved tab IDs are regenerated by normalization (`mt-layout/src/lib.rs:1573`). A visible terminal tab can legitimately share its owner `TabId` with another visible terminal tab; distinguish them by pane key and carry the complete original target.
- `SplitNode` node IDs are process-local and are not the routed pane identity (`tree.rs:20`, `persist.rs:65`). Do not key persistent flat selection/order by leaf ID, ordinal, title, shell, or numeric PTY handle.

### Minimal Projection and Selection

1. **Inventory:** For the current exact project/worktree binding, iterate `state.panels` in saved order and `panel.layout.panes()` in DFS/leaf-vector order. `ProjectState::all_panes` already covers this entire inventory (`store/mod.rs:203`); use the panel-aware traversal when constructing targets. Never use only `active_layout()` or `visible_panes()`: the former omits other panels and the latter includes only each leaf's active pane (`tree.rs:329`, `tree.rs:371`). Include dormant and exited/error records as well as attached terminals.
2. **Row target:** Reuse `TerminalJumpTarget` and the target construction pattern in `terminal_jump_views` (`store/context.rs:427`, `store/context.rs:452`). It carries project, host, worktree, original tab, pane, session and optional incarnation. Labels/status are projections; `pane_display_label` preserves project-aware/remote label behavior (`store/context.rs:486`). Do not project the panel's count/status/custom title as though the row were still a group. Avoid calling the all-project jump builder as a per-frame global inventory scan when a small scoped projection suffices.
3. **Remember one terminal:** Add an optional field such as `selected_terminal_pane_key` / `selectedTerminalPaneKey` to the existing runtime/saved layout, not to `Workspace` or the right tool selection. The new field selects a logical pane; it should not persist an incarnation, because explicit reconnect legitimately rotates that incarnation. Complete incarnation fencing belongs to captured action targets.
4. **Why the field is needed if trees stay intact:** Today the only singular focus is window-global `focused_pane_id` (`store/mod.rs:390`). `active_pane_id` falls back to the first active pane of the active panel when global focus belongs elsewhere (`store/panes.rs:593`, `tree.rs:453`). Every legacy leaf independently persists `activePaneKey` (`persist.rs:37`), so the saved state cannot distinguish which leaf supplied the single selected terminal. Two leaves can both retain active panes without any serialized winner.
5. **Fallback:** Prefer a valid new pointer within the exact bound layout. When initializing from live state without it, preserve the current valid focused pane first. For legacy cold state, use restored active panel plus its first active pane; this is an unavoidable deterministic choice because older JSON never recorded the focused leaf. If a pointer disappears after close/salvage, select a deterministic surviving flat neighbor, or the ordinary legacy fallback when no previous flat position exists. Empty inventory yields the existing empty state, not a replacement terminal.
6. **Keep compatibility pointers synchronized:** Selecting a row updates its original owner as `active_panel_id`, activates that pane in its original leaf, and records the new worktree-layout selection. Persist these together. `activate_pane_inner` already resolves the owner across all panels, clears IME preedit, activates the leaf, focuses and saves (`store/panes.rs:473`). Extend that boundary and the already-attached variant, rather than assigning focus alone in a titlebar click callback.
7. **Creation/close ordering:** `new_terminal_with_cwd` currently saves through `after_layout_change` *before* its `focus_pane` call (`store/panes.rs:161`); `focus_pane` only changes global focus and focuses an entity (`store/panes.rs:572`). A new selected-pointer update performed only after that save would persist stale selection. Creation, explicit activation and close fallback need one consistent update-before-save policy. Closing an unselected terminal must not change the selected pane even if an internal leaf chooses a different active child (`store/panes.rs:395`, `store/mod.rs:242`).

The runtime compatibility map is still `HashMap<String, ProjectState>` keyed by project ID (`store/mod.rs:377`), whereas persistence is worktree-bound. Keep the new field with the existing layout snapshot/binding and reuse `layout_dirty_worktree_owners`; do not silently turn this UI task into a migration of all `project_states` or a merge of separately attached aliases. Same-worktree aliases need explicit regression coverage against the existing latest-owner policy (`store/layout.rs:518`, `store/mod.rs:367`).

**Hydration is a separate behavior from rendering.** Current ordinary project/panel activation hydrates every eligible dormant pane in the active legacy panel, not merely its visible panes (`store/projects.rs:106`, `store/layout.rs:253`, `store/panes.rs:704`). Dormant terminal-jump activation explicitly invokes this same path even when its panel is already active (`store/context.rs:565`). Live exact activation skips it. Therefore:

- A flat titlebar click to an attached terminal should preserve the existing exact-live path, entity, PTY handle, session and incarnation, with no call that respawns/reconnects it.
- Merely drawing an inventory must not hydrate every panel or replace any pane. Keep existing recovery/resume logic and remote hydration gates.
- **Selected-only hydration is not required to flatten rendering.** Leaving ordinary dormant-panel hydration intact is the minimum lifecycle change, but the plan must not claim it hydrates exactly one terminal. If a later approved design also requires that behavior, factor the existing pending-pane/recovery loop into a targeted path using the pane's original `TabId`; select before hydration, handle already-active-panel early returns, and preserve warm-attach/cold-restore/resume semantics (`store/panes.rs:757`, `store/panes.rs:784`). Do not alter background lifetime as a side effect.

### Render Only the Selected Terminal

- `TerminalArea` currently snapshots only `store.active_layout()` (`terminal_area.rs:3036`), recursively renders all split children (`terminal_area.rs:1105`), or maximizes one leaf while showing other collapsed leaf bars (`terminal_area.rs:1253`). **Always-maximized mode does not meet the request**: it retains group navigation and still relies on leaf membership.
- Extract/reuse the selected terminal body behavior from `render_leaf` (`terminal_area.rs:2302`), with the existing entity lookup at `terminal_area.rs:2335`. Do not implement a synthetic one-pane `ProjectPanel` and install it into the store merely to reuse a renderer.
- Preserve selected-pane search, markers, reconnect/error presentation and file-path drops. Reconnect detection/overlay is at `terminal_area.rs:2352`; internal/external file drops intentionally write through `AppStore::write_to_pane` at `terminal_area.rs:2466`. Removing pane split-drop handling must not remove file-drop handling.
- Remove leaf tab bars from the terminal body when moving tabs to the titlebar, plus collapsed-leaf navigation and maximize/restore machinery from the rendering path. Keep the existing terminal/document/work-item page boundary; the generic terminal page tab in `workbench_area.rs:1392` is a separate integration point if avoiding redundant terminal navigation, not a reason to redesign document storage.
- **Transition trap:** leaf tab swaps mount the old terminal entity (`terminal_area.rs:2338`), and panel transitions can render the old panel's whole split tree (`terminal_area.rs:3402`). Routing normal content through a selected-only renderer is insufficient if those exit layers remain. The simplest compliant transition draws only the selected terminal; any retained motion or snapshot preview must not mount another live terminal entity or resurrect split rendering.
- `AppStore` holds all terminal entities and subscriptions independently of what is rendered (`store/mod.rs:378`, `store/mod.rs:387`). A document page already hides the terminal view without removing these owners (`workbench_area.rs:1`, `workbench_area.rs:1607`). Preserve that lifetime pattern. Disposal removes routes, polling, entities and subscriptions (`store/ai.rs:347`); it is not part of tab switching.
- Background lifetime/accounting must keep traversing all panes/routes: `pty_in_any_layout` (`store/ai.rs:368`), `live_pane_ids` (`store/layout.rs:492`), and SSH Agent polling (`store/remote_agents.rs:278`) must not consume the new selected-only display inventory.
- Titlebar tabs and their close/menu controls must be outside the existing drag-marked center (`title_bar.rs:910`) and native window controls (`title_bar.rs:917`). Keep stable pane-key-based element/focus identities; the old tabs already preserve keyboard activation (`terminal_area.rs:1691`). Long-title/overflow geometry is a later UI acceptance item, not evidence established here.

### Flat Ordering Without Route Reparenting

The initial flat order can be completely derived from existing panel/DFS order, with no new order storage. Current tab movement is not general flat reorder: both `move_pane` and `move_pane_to_tab` operate only on `active_layout()` (`store/panes.rs:268`, `store/panes.rs:300`). The drag payload carries only project ID and pane ID (`dnd.rs:87`), and acceptance checks only project ID (`terminal_area.rs:2700`).

If retaining unrestricted titlebar drag reorder is part of the approved interaction, add an optional worktree-layout `terminalOrder: Vec<PaneKey>` projection order. Reordering changes that list only, never `ProjectPanel` ownership. Derive absent order from panel/DFS traversal; ignore stale/duplicate keys and append all currently missing inventory members deterministically so an old/incomplete order cannot strand a terminal. Cycle/index navigation and post-close neighbor choice must use this same order. Save through the existing layout writer. Validate both drag endpoints against the original project/worktree and exact live/saved terminal targets before mutation.

If that ordering behavior is not approved, omit pane dragging from the new strip rather than leaving an apparent cross-panel reorder which silently fails or moves a terminal to a new `TabId`. Do not restrict users by exposing hidden panel boundaries as reorder groups.

### Persistence Boundary and Smaller Alternative

- Preserve `SavedProjectLayout.tabs`, original `SavedTab.tabId`/`customTitle`, full `splitLayout`, leaf `activePaneKey`, and every saved pane's session/incarnation/CWD/AI record (`mt-config/src/config.rs:331`, `mt-config/src/config.rs:370`, `persist.rs:20`). Selection changes should not regenerate IDs, rebuild panes with `PaneState::new`, discard background panels, or flatten the serialized inventory into only the selected tab.
- For the recommended additive selector, use the existing optional/defaulted serde pattern (`mt-config/src/config.rs:400`). Read/write it in `persist::serialize_layout` / `restore_layout`, startup/reconciled-layout installation (`store/identity.rs:127`), and the existing layout snapshot producer (`store/layout.rs:518`). Also teach salvage and stable-pointer normalization about it (`mt-layout/src/lib.rs:1300`, `mt-layout/src/lib.rs:1536`). Optional order, if chosen, needs the same complete handling. Malformed selection/order metadata must not invalidate healthy terminal records.
- Existing `activeTabId` and `activeTabIndex` remain the selected pane's **legacy owner** for old readers, while the selected pane's own leaf active key is updated. A valid new selector can locate its owner across the layout; normalize compatibility pointers together. If selection is invalid, repair the pointer, not the surviving panes' identity.
- `save_bound_layout_in` writes both the worktree row and legacy project mirror (`mt-layout/src/lib.rs:1195`, `mt-layout/src/lib.rs:1216`). Reuse this transaction and the explicit latest dirty alias; do not introduce a separate titlebar database/preference writer. Adding optional JSON fields alone does not require a new SQLite table or a schema rebuild.
- Old binaries can still read all old terminal records/geometry. Their typed save may omit the new selection/order fields; that downgrades flat-selection/order memory, not the terminal inventory. Do not promise new-field round trips through an unmodified older writer. After re-upgrade the deterministic fallback must work.

**Alternative, not selected:** It is route-compatible in principle to collapse *each individual existing panel's own* leaves into one leaf of the same `PaneState` values while preserving that panel's `TabId`. Then existing `activeTabId` plus that single leaf's `activePaneKey` can represent the one selected terminal without a new selector field. This is distinct from merging panels or allocating one panel per old terminal. Source support: routes contain the panel and pane identities, not leaf node IDs (`store/identity.rs:454`), and terminal entities live outside the trees (`store/mod.rs:378`).

However, that alternative permanently normalizes saved split geometry and leaf-specific active pointers, needs careful initial selection/empty-leaf cleanup, and still does not solve arbitrary cross-panel flat reorder. It is only the smaller-schema option if loss of old geometry is explicitly acceptable. The recommended projection plus selector keeps rollback data intact and avoids a live-tree migration solely for presentation.

8. **Mobile/background append:** Start sessions with empty/nonempty legacy layouts while a different pane, document or worktree has focus. Inventory gains exactly the created pane; desktop focus/selection does not change. Returned pane ID, launcher command, rename/write and acknowledgement remain exact. Existing mobile inventory is already across all panels (`mobile_relay.rs:773`); do not regress it to the displayed terminal. Preserve SSH/WSL launcher guards (`mobile_relay.rs:916`).
9. **Persistence/salvage/rollback:** Round-trip old single-pane `pane` JSON, multi-pane leaves and multiple panels with distinct owner IDs and selection. Retain every valid session/CWD/AI record, owner ID, size/direction and legacy title. Corrupt only the new selector/order, test surviving terminals remain; normalize idempotently and dual-write the worktree/mirror. Include same-worktree latest-owner and alias-removal cases (`store/layout.rs:739`, `store/layout.rs:796`; salvage at `mt-layout/src/lib.rs:1300`).
10. **UI/focus integration using Actions artifacts:** Long/duplicate/Unicode labels, overflow, narrow/wide windows and platform window controls; tab activation versus window dragging; Enter/Space, Ctrl+Tab/Shift+Tab and Ctrl+1..9 across all owners; terminal IME and raw Tab/Escape input; search/markers, selected SSH reconnect/error state, internal/external file drops, document dirty-state/focus return.
